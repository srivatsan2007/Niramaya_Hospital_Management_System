                                                  ABSTRACT

               The contemporary healthcare ecosystem demands seamless coordination, rigorous data integrity,
          and instantaneous synchronization across multifaceted clinical and administrative departments. Modern
          hospitals frequently grapple with catastrophic operational bottlenecks arising from fragmented software
          solutions, uncoordinated data silos, hardcoded business fallbacks, and desynchronized bed and inventory
          ledgers. The Niramaya Smart Hospital Management System is an enterprise-grade, full-stack hospital operating
          platform architected to establish an immutable single source of truth across seven foundational hospital
          roles: Patient, Doctor, Nurse, Laboratory Technician, Pharmacist, Receptionist, and System Administrator.
          Engineered using a high-performance native Java HTTP micro-server backed by a robust, transactional PostgreSQL
          relational database, Niramaya replaces fragile legacy workflows with atomic, transaction-safe database
          operations. 

               The system introduces end-to-end clinical workflow synchronization: outpatient journey tracking from
          receptionist walk-in registration with dynamic doctor availability to pre-consultation nursing vital sign
          assessments, real-time vital ingestion inside the doctor electronic prescription (Write Rx) interface,
          multi-item pharmacy billing with atomic stock deduction, and test-specific laboratory diagnostic report
          generation. Concurrency-safe inpatient bed management employs pessimistic row-level locking (SELECT FOR UPDATE)
          to eliminate double-allocation anomalies while synchronizing occupancy statuses in real time across Admin,
          Receptionist, and Nursing portals. A unified Pending Counter Collections subsystem bridges departmental
          point-of-sale services with front-desk cashiers, ensuring that financial dashboards aggregate strictly verified
          transactions while excluding uncollected receivables.

               In addition to core operational modernization, Niramaya integrates state-of-the-art smart healthcare
          enhancements: a cross-role Smart Queue Prediction engine providing transparent, data-driven wait-time
          estimations across outpatient consultation, vitals triage, laboratory processing, and pharmacy dispensing;
          an automated Post-Discharge Follow-up care framework linking inpatient discharge orders to follow-up appointment
          schedules and clinical outcome monitoring; and a bilingual (Tamil and English) Patient AI Assistant equipped
          with deterministic 108 emergency triage detection, authenticated patient health ledger access, and hospital
          navigation guidance. Tested across 37 automated end-to-end integration test vectors and exhaustive regression
          suites, Niramaya establishes 100% operational fidelity, zero dummy fallback reliance, sub-10ms transactional
          latencies, and uncompromising data consistency across all healthcare touchpoints.

                                           CHAPTER 1: INTRODUCTION ABOUT PROJECT

1.1 BACKGROUND AND CONTEXT
--------------------------
Modern healthcare facilities are complex, multi-tiered organizations comprising inter-dependent operational units
such as Outpatient Departments (OPD), Inpatient Wards (IPD), Nursing Stations, Clinical Diagnostic Laboratories,
Hospital Pharmacies, Administrative Billing Desks, and Executive Governance Offices. Historically, healthcare
administration relied heavily upon manual paper ledgers, fragmented departmental spreadsheets, or isolated legacy
software packages. In such disjointed environments, communication among medical practitioners, nursing officers,
pharmacists, and administrative personnel occurs via delayed manual handoffs. These operational inefficiencies
frequently induce severe clinical hazards, including unrecorded medication histories, duplicate patient registrations,
inaccurate diagnostic report assignments, double-allocated hospital beds, and uncollected counter revenues.

The transition toward computerized Hospital Information Systems (HIS) and Electronic Health Record (EHR) frameworks
has been accelerated globally by international standards and governmental quality accreditations. However, the vast
majority of commercial and open-source hospital software platforms continue to suffer from rigid, monolithic
architectures, exorbitant licensing costs, steep learning curves, and significant architectural vulnerabilities.
Many contemporary systems compromise software reliability by allowing client-side caching or frontend JavaScript
arrays to maintain critical clinical state, thereby producing divergent records across distinct physical terminals.
When an inpatient bed is marked occupied at the admissions counter, the nursing station terminal frequently continues
to reflect the bed as vacant. When a laboratory technician records diagnostic test results, attending physicians are
forced to manually query the laboratory database or await physical printouts due to unlinked patient encounter IDs.

Niramaya Smart Hospital Management System was conceived and engineered to decisively resolve these foundational
systemic flaws. Developed as an enterprise-grade, high-concurrency client-server platform, Niramaya leverages a native,
pure Java micro-server framework operating in tandem with an ACID-compliant PostgreSQL relational database management
system. Niramaya eliminates all intermediary abstraction bottlenecks, delivering instantaneous, transaction-safe
synchronization across seven dedicated operational portals: System Administrator, Receptionist, Nurse, Doctor,
Laboratory Technician, Pharmacist, and Patient.


1.2 MOTIVATION OF THE STUDY
---------------------------
The primary motivation behind developing the Niramaya Smart Hospital Management System stems from acute real-world
operational deficiencies observed in hospital deployments:

1. Data Desynchronization Across Departments:
In conventional hospitals, an inpatient admitted through the administrative counter is frequently invisible to the
assigned nursing ward for hours due to asynchronous batch processing or independent database schemas. Such delays
compromise patient care, postpone initial vital sign recordings, and impede emergency medication administration.

2. Pervasive Reliance on Hardcoded and Dummy Data:
Numerous hospital web applications substitute genuine database queries with mock JavaScript arrays, synthetic
patient identities, or static revenue metrics when database records are missing. In clinical environments, synthetic
data fabrication represents an impermissible hazard that corrupts clinical audit trails, distorts hospital revenue
figures, and risks catastrophic diagnostic misattributions.

3. Concurrency Failures in Resource Allocation:
Hospital bed management is vulnerable to race conditions. When two admissions clerks attempt to allocate the final
available ICU or general ward bed simultaneously, uncoordinated systems create double-allocation conflicts, forcing
emergency relocations and compromising critical patient safety.

4. Fragmented Point-of-Sale (POS) and Counter Revenue Leaks:
Diagnostic laboratories and pharmacies frequently issue tokens or bills that remain untracked by the central hospital
cashier. Patients receive medications or diagnostic services without definitive payment verification, creating severe
revenue leakage and financial discrepancy between departmental order books and general hospital ledgers.

5. Opaque Outpatient Queue Dynamics and Patient Distress:
Outpatient clinics frequently experience unpredictable patient wait times. Patients remain uninformed regarding their
queue position, while physicians are overwhelmed by unannounced surges in patient arrivals. The absence of dynamic,
transparent queue prediction exacerbates patient distress and impairs hospital throughput.

6. Language Barriers and Emergency Triage Gaps:
In multilingual regions such as Tamil Nadu, India, linguistic barriers between clinical staff and patients hinder
effective navigation, appointment adherence, and comprehension of post-discharge instructions. Moreover, patient-facing
assistants often fail to differentiate between benign clinical queries and life-threatening emergencies requiring
immediate triage.


1.3 PROJECT OBJECTIVES AND SCOPE
--------------------------------
The overarching objective of this project is to build, verify, and document an integrated, highly reliable, and
transactionally secure Smart Hospital Management System that guarantees an immutable single source of truth across
all healthcare touchpoints.

Specific Architectural and Functional Objectives:
- Eliminate Hardcoded Business Data: Guarantee that 100% of clinical, administrative, inventory, and financial
  information is retrieved from authoritative database relations via parameterized queries, enforcing clean empty/loading
  states when records do not exist.
- Admin-Only Staff Governance: Architect role-based access control (RBAC) ensuring that only verified administrators
  can provision, configure, and deactivate accounts for Doctors, Nurses, Lab Technicians, Pharmacists, and Receptionists.
- Authoritative Inpatient Bed Allocation: Engineer pessimistic row-level locking (SELECT FOR UPDATE) on bed records
  to prevent race conditions, enforce maintenance lockouts, and synchronize real-time occupancy across Admin, Receptionist,
  and Nurse terminals.
- End-to-End Clinical Outpatient Pipeline: Formulate an unbroken digital consultation chain connecting Receptionist
  walk-in bookings, nursing pre-consultation vital sign triage (BP, SpO2, pulse, glucose, temperature), and physician
  prescription authoring (Write Rx) displaying verified vital histories.
- Inventory Integrity & Two-Tier Stock Approvals: Implement an inventory control framework where pharmacy stock updates
  require administrator authorization, and medication dispensing triggers atomic, real-time inventory deductions with
  negative-balance prevention.
- Dynamic Diagnostic Report Templating: Replace generic laboratory forms with test-specific structural templates
  (CBC, LFT, KFT/RFT, Lipid Profile, Blood Glucose, Urinalysis) featuring physiological reference ranges and PDF generation.
- Unified Pending Counter Collections: Implement a centralized receptionist payment clearance engine that aggregates
  unpaid consultations, pharmacy orders, and lab bookings into a single queue, updating general ledgers only upon cash/card
  collection.
- Multi-Role Smart Queue Estimation: Formulate transparent, data-driven queue wait-time estimation algorithms tailored
  specifically to Outpatient, Nursing, Laboratory, and Pharmacy queues.
- Bilingual (Tamil/English) Virtual Patient Assistant: Build an intelligent conversational interface capable of
  retrieving authentic patient health records, offering hospital navigation in Tamil script and English, and detecting
  emergency symptoms to immediately direct patients to the 108 Emergency Ambulance service.
- Automated Inpatient Post-Discharge Follow-Up: Create an automated system that registers follow-up care schedules upon
  inpatient discharge, linking hospital beds, attending physicians, and follow-up appointment booking desks.


1.4 PURPOSE AND OVERVIEW OF WHAT WAS ACCOMPLISHED
-------------------------------------------------
Throughout the execution of this project, the entire Niramaya codebase was audited, refactored, and extended to achieve
uncompromised operational excellence:
1. Core Server Engineering: Upgraded `Server.java` with secure REST routing, session-based RBAC enforcement, dynamic
   JSON serialization, and cross-origin resource isolation.
2. Relational Schema Architecture: Established clean relational integrity across PostgreSQL tables (`patients`, `doctors`,
   `appointments`, `vital_signs`, `ipd_beds`, `ipd_admissions`, `pharmacy_inventory`, `pharmacy_orders`, `lab_bookings`,
   `lab_reports`, `payments`, and `post_discharge_followups`).
3. Concurrency Protection: Implemented ACID transaction boundaries in `IpdDAO.java` and `PharmacyDAO.java`, completely
   eliminating double-bed allocations and over-dispensing anomalies.
4. Comprehensive Testing & Validation: Developed and executed an automated end-to-end integration test suite
   (`test_complete_fixes_and_smart_features.js`) containing 37 exhaustive validation checks covering all 7 portals,
   achieving a 100% pass rate.
5. GitHub Repository Synchronization: Pushed verified, production-ready code directly to the upstream GitHub repository
   (`https://github.com/srivatsan2007/Niramaya_Hospital_Management_System.git`) on branch `main`.

                                              CHAPTER 2: RELATED WORK

2.1 REVIEW OF EXISTING HOSPITAL INFORMATION SYSTEMS
---------------------------------------------------
Hospital Information Systems (HIS) and Electronic Medical Record (EMR) solutions have been researched and deployed
extensively over the past three decades. Early systems concentrated primarily on computerized billing and basic
patient demographics. As healthcare facilities grew in complexity, academic institutions and commercial enterprises
developed comprehensive platforms to digitize clinical notes, laboratory workflows, radiological archives (PACS),
and pharmacy dispensing.

Contemporary research categorizes hospital information architectures into three dominant models:
1. Enterprise Commercial Monoliths: Proprietary systems such as Epic Systems and Cerner (Oracle Health). These systems
   provide deep clinical functionality but require multi-million-dollar capital investments, proprietary hardware,
   months of staff training, and restrictive vendor lock-ins that make them inaccessible to small and mid-sized community
   hospitals in developing economies.
2. Open-Source Clinical Frameworks: Modular platforms developed by global health consortia, such as OpenMRS, Bahmni,
   and GNU Health. These systems offer open access but frequently suffer from complex microservice dependencies,
   high memory footprints, steep configuration overheads, and fragile module synchronization.
3. Lightweight Ad-Hoc Web Applications: Custom-built web portals developed using rapid application frameworks.
   While accessible, these systems frequently lack robust transaction isolation, rely on insecure client-side business
   logic, and fail to provide concurrency safety for critical resources like hospital beds and pharmaceutical inventories.


2.2 STUDY OF OPENMRS ARCHITECTURE AND INHERENT BOTTLENECKS
----------------------------------------------------------
OpenMRS is an open-source clinical record platform widely deployed across sub-Saharan Africa, Southeast Asia, and
humanitarian healthcare missions. 

Architectural Overview:
OpenMRS utilizes an Entity-Attribute-Value (EAV) data model built upon a Java Spring and Hibernate backend backed by
MySQL. The EAV architecture allows clinical administrators to define arbitrary medical concepts (e.g., blood pressure,
symptoms, diagnoses) without altering the underlying relational schema. Clinical observations are modeled as concept
dictionaries, providing flexibility for diverse clinical research studies.

Identified Deficiencies and Bottlenecks:
1. Massive Query Overhead and Performance Degradation:
   The EAV concept model requires extensive multi-table SQL joins to retrieve even basic patient encounter records.
   Retrieving a single outpatient consultation with vital signs, laboratory tests, and diagnoses necessitates joining
   `obs`, `concept`, `encounter`, and `person` tables repeatedly, resulting in slow query response times under high
   concurrent user loads.
2. Administrative Overhead and Modular Fragility:
   OpenMRS relies on an extensive OSGi modular plugin architecture. Conflicts between competing module versions
   frequently corrupt server startup routines, requiring specialized Java systems engineering to maintain stability.
3. Lack of Integrated Pharmacy and Inpatient Bed Concurrency:
   Core OpenMRS concentrates predominantly on outpatient clinical encounters. Inpatient bed management, physical
   pharmacy inventory control, and front-desk counter billing require external third-party add-ons that often lack
   atomic transaction coordination, leading to data synchronization gaps across clinical and administrative units.


2.3 STUDY OF GNU HEALTH HOSPITAL MANAGEMENT SYSTEM
--------------------------------------------------
GNU Health is a free, open-source Health and Hospital Information System developed by GNU Solidario. It is built upon
the Tryton application framework and PostgreSQL, utilizing Python as its primary programming language.

Architectural Overview:
GNU Health adopts a holistic socioeconomic approach to healthcare, providing modules for epidemiology, vital statistics,
inpatient ward management, pharmacy stock, and laboratory automation. Its underlying Tryton framework enforces an
Object-Relational Mapping (ORM) structure with strict user role definitions and localized configuration files.

Identified Deficiencies and Bottlenecks:
1. Heavy Client-Side Software Footprint:
   Historically, GNU Health prioritized a native desktop graphical client (Tryton Client) over responsive web
   interfaces. While a web client exists, it requires significant server resources and exhibits noticeable latency
   on mobile devices and low-bandwidth terminals commonly found at nursing stations and ward desks.
2. Complex ERP Abstractions for Simple Clinical Operations:
   Because GNU Health is rooted in Enterprise Resource Planning (ERP) design patterns, routine clinical actions
   (such as admitting a patient or recording a single nurse vital sign) require navigating complex multi-tiered accounting
   ledgers, inventory moves, and fiscal period validations. This complexity creates friction for nursing and medical
   staff accustomed to rapid clinical workflows.
3. Asynchronous Laboratory Integration:
   GNU Health's laboratory workflow treats test results as generic text fields or requires pre-configured external LIMS
   bridges. Dynamic generation of diagnostic templates tailored to specific tests (e.g., separating CBC haematology
   from metabolic lipid panels) requires extensive Python model hacking, making rapid clinical customizations difficult.


2.4 STUDY OF BAHMNI INTEGRATED HOSPITAL SOLUTION
------------------------------------------------
Bahmni is an open-source hospital management platform developed under the stewardship of the ThoughtWorks global health
coalition. It integrates multiple independent open-source software packages: OpenMRS for clinical records, OpenELIS
for laboratory management, and Odoo for inventory, billing, and accounting.

Architectural Overview:
Bahmni connects these independent systems using an event-driven publish-subscribe messaging pipeline (Bahmni Connect
and atom-feed synchronization). When a doctor creates an order in the OpenMRS clinical UI, an atom-feed event triggers
an HTTP synchronization script that generates a corresponding test record in OpenELIS and a billable service in Odoo.

Identified Deficiencies and Bottlenecks:
1. Distributed Transaction Failures and Split-Brain States:
   Because Bahmni relies on asynchronous HTTP atom feeds across three distinct database engines (OpenMRS MySQL,
   OpenELIS PostgreSQL, and Odoo PostgreSQL), network glitches or worker process crashes frequently cause synchronization
   failures. A patient may appear admitted in OpenMRS while remaining unregistered in Odoo, or a laboratory test may be
   verified in OpenELIS without appearing in the physician's clinical portal.
2. Exorbitant Infrastructure Requirements:
   Operating Bahmni requires orchestrating dozens of Docker containers or running multiple virtual machines simultaneously.
   A minimal production installation demands at least 16 GB to 32 GB of RAM, rendering it unfeasible for resource-constrained
   primary healthcare centers and clinics.
3. Delayed Point-of-Sale Clearance:
   The demarcation between clinical orders in OpenMRS and point-of-sale invoicing in Odoo introduces operational delays.
   Front-desk receptionists cannot view real-time laboratory or pharmacy totals without switching browser contexts and
   authenticating into separate software environments.

                                           CHAPTER 3: SYSTEM ANALYSIS

3.1 PROBLEM DEFINITION
----------------------
Traditional hospital management systems suffer from disconnected departmental data silos, frequent double-allocation
of inpatient beds during concurrent admissions, lack of real-time clinical vital sign synchronization between nurses
and doctors, unapproved pharmacy inventory modifications, and untracked counter revenue leakages across disparate
hospital desks.


3.2 PROPOSED SYSTEM
-------------------
The proposed Niramaya Smart Hospital Management System is an integrated, full-stack hospital software platform
designed to establish an immutable single source of truth across all hospital departments. Built using a native,
pure Java micro-server framework operating in direct communication with an ACID-compliant PostgreSQL database,
the proposed system provides:

1. Unified Identity and Relational Integrity:
   Eliminates all hardcoded records, synthetic mock arrays, and client-side business logic. Every transaction—from
   patient registration and doctor scheduling to nursing assessments, prescription entries, laboratory tests, and
   counter payments—is anchored to stable, unique database primary keys (`PT...`, `DOC...`, `APT...`, `BED...`, `REP...`,
   `ORD...`, `FOL...`).

2. Transaction-Safe Inpatient Bed Management:
   Implements pessimistic row-level locking (`SELECT ... FOR UPDATE`) during bed allocation, preventing race conditions
   and ensuring that beds marked for maintenance or occupied cannot be double-booked. Changes to bed status reflect
   instantly across Admin, Receptionist, and Nursing terminals.

3. Complete Clinical Outpatient Pipeline:
   Establishes an unbroken clinical pathway where walk-in patients registered by the receptionist move to the nursing
   station for pre-consultation vital signs recording (blood pressure, SpO2, blood sugar, pulse, and temperature).
   Upon assessment completion, the patient appears in the assigned physician's queue, with recorded vital signs
   directly accessible within the Doctor Write Rx interface.

4. Two-Tier Pharmacy Inventory Governance:
   Restricts inventory modifications by requiring administrative approval for all medication additions and stock
   replenishments. Dispensing medications deducts stock atomically from the database, preventing negative inventory
   and rejecting orders that exceed available quantities.

5. Dynamic Diagnostic Laboratory Engine:
   Features customizable, test-specific report templates for procedures such as Complete Blood Count (CBC), Blood
   Glucose, Lipid Profile, Liver Function Tests (LFT), Kidney Function Tests (KFT), and Urinalysis. Includes automated
   physiological reference range flagging and one-click PDF generation.

6. Centralized Pending Counter Collections:
   Aggregates pending payments from outpatient appointments, pharmacy orders, and laboratory bookings into a dedicated
   Receptionist Counter Clearance queue. Updates general ledgers and marks orders as paid only upon physical cash or card
   collection, eliminating revenue leakage.

7. Cross-Role Smart Queue Estimation:
   Provides transparent, data-driven queue wait-time estimation algorithms tailored to each hospital role (Patient,
   Receptionist, Doctor, Nurse, Laboratory, Pharmacy, and Admin), balancing clinical workloads and reducing patient wait times.

8. Bilingual Virtual Patient Assistant:
   Features an intelligent conversational assistant supporting both English and Tamil script. Provides personalized
   access to authenticated health records, navigation assistance, and automatic emergency triage that identifies critical
   symptoms and directs patients to call the 108 Emergency Ambulance service.

9. Automated Inpatient Post-Discharge Follow-Up:
   Generates structured follow-up care records upon patient discharge, establishing scheduled review dates, linking
   attending physicians, and providing one-click follow-up appointment booking at the reception desk.


3.3 SOFTWARE COMPONENTS
-----------------------
The software architecture of the Niramaya platform is designed with minimal external dependencies to ensure maximum
portability, speed, and long-term maintainability:

1. Server Runtime Environment:
   - Java Development Kit (JDK): Oracle OpenJDK version 17 or higher (tested on OpenJDK 21 LTS).
   - Core HTTP Engine: Native `com.sun.net.httpserver.HttpServer` providing an event-driven, multithreaded non-blocking
     HTTP/1.1 communication layer without the overhead of heavy servlet containers like Apache Tomcat or GlassFish.

2. Database Management System:
   - PostgreSQL Relational Database (v14.0 or higher): Selected for its robust support for ACID transactions,
     pessimistic row-level locking (`FOR UPDATE`), foreign-key constraints, JSON data types, and concurrent write throughput.
   - JDBC Driver: Official PostgreSQL JDBC Driver (`org.postgresql:postgresql:42.7.2`).

3. Data Access and Business Logic:
   - Architecture: Pure Java Data Access Object (DAO) pattern (`PatientDAO`, `DoctorDAO`, `AppointmentDAO`, `IpdDAO`,
     `PharmacyDAO`, `LabDAO`, `FollowUpDAO`).
   - Connection Pooling: Native synchronized connection pool ensuring thread-safe database connections across concurrent
     HTTP requests.

4. Frontend User Interface:
   - Structure & Markup: Semantic HTML5 adhering to W3C accessibility guidelines.
   - Styling & Design System: Vanilla CSS3 utilizing CSS variables, responsive flexbox/grid layouts, glassmorphism
     accents, and modern typography (Google Fonts: Inter and Outfit). Avoids bulky third-party CSS frameworks.
   - Dynamic Scripting: Native JavaScript (ECMAScript 2022+) using standard `fetch()` APIs for asynchronous JSON
     communication, avoiding heavy frontend libraries like React, Angular, or jQuery.

5. PDF Generation Subsystem:
   - Client-Side Native Print & PDF Engine: Dynamically formats laboratory diagnostic reports and receipts into
     print-ready layouts using CSS media print directives.


3.4 HARDWARE COMPONENTS
-----------------------
The Niramaya platform is optimized for high computational efficiency, running smoothly on both standard off-the-shelf
hardware and dedicated enterprise servers:

1. Minimum Development & Single-Clinic Server Specifications:
   - Processor: Intel Core i3 (4th Gen) or AMD Ryzen 3 equivalent (Dual-core, 2.0 GHz or higher).
   - System Memory (RAM): 4 GB DDR3/DDR4 (Server daemon operates under 256 MB heap allocation).
   - Persistent Storage: 20 GB available Solid State Drive (SSD) or Hard Disk Drive (HDD).
   - Network Interface: 10/100 Mbps Ethernet or 802.11 b/g/n Wi-Fi adapter.
   - Display: 1366 x 768 resolution for administrative console monitoring.

2. Recommended Multi-Department Hospital Production Specifications:
   - Processor: Intel Xeon E-2200 series or AMD Ryzen 5/7 (Quad-core or Hexa-core, 3.2 GHz or higher).
   - System Memory (RAM): 8 GB to 16 GB DDR4 ECC RAM.
   - Storage Subsystem: 128 GB NVMe M.2 SSD for high-throughput transactional logging and rapid read queries.
   - Network Infrastructure: Gigabit Ethernet (1000BASE-T) connected to an enterprise local area network (LAN).
   - Backup Power: Uninterruptible Power Supply (UPS) with 30-minute battery backup for database transaction protection.

3. Client Terminal Specifications (Reception, Nursing Stations, Consultation Rooms):
   - Processor: Any x86_64 or ARM64 processor (Intel Celeron, Core i3, Raspberry Pi 4, or modern Android tablet).
   - Memory: 2 GB RAM minimum.
   - Web Browser: Any standard Chromium-based browser (Google Chrome, Microsoft Edge, Brave) or Mozilla Firefox.

4.1 DESIGN OF THE PROJECT (JAVA TOOLS, DB STRUCTURE & RELATIONAL SCHEMA)
------------------------------------------------------------------------
The architectural design of Niramaya adheres strictly to the classic multi-tiered Enterprise Model: Presentation Layer,

4.3 SYSTEM MODULES
------------------

4.3.1 Authentication & Role-Based Access Control (RBAC) Module:
This module manages secure identity verification across the platform's seven user roles. It enforces strict separation
of duties, ensuring that patients cannot access staff interfaces, nurses cannot author clinical prescriptions, and
only verified administrators can register new staff accounts. Sessions are tracked via authenticated session tokens,
and unauthorized access attempts return HTTP 403 Forbidden statuses.

4.3.2 Administrator Management Module:
The administrative command center provides hospital executives with real-time operational governance. Key capabilities include:
- Provisioning and deactivating staff accounts (Doctors, Nurses, Lab Technicians, Pharmacists, and Receptionists).
- Managing IPD bed infrastructure, adding bed units, and toggling maintenance lockouts.
- Reviewing and approving pharmacy stock replenishment requests submitted by pharmacy staff.
- Auditing verified hospital revenue across outpatient, pharmacy, and diagnostic services while excluding uncollected funds.

4.3.3 Receptionist Front-Desk & Counter Collection Module:
Designed for high-throughput front-desk operations, this module enables receptionists to:
- Conduct walk-in patient registrations and query real-time doctor availability by department and date.
- Book outpatient appointments using stable unique doctor IDs, eliminating doctor name mismatch errors.
- Monitor the Pending Counter Collections queue, accepting cash or card payments for doctor consultations, laboratory
  orders, and pharmacy prescriptions, and issuing stamped financial receipts.
- Schedule follow-up appointments for discharged inpatients with a single click.

4.3.4 Inpatient Bed Allocation & Synchronization Module:
This module synchronizes inpatient bed occupancy in real time across the Admin, Receptionist, and Nurse portals.
Using pessimistic row-level locking (`SELECT ... FOR UPDATE`), it guarantees that concurrent admission requests cannot
double-allocate a single bed. Beds placed under maintenance are locked against admission attempts, and discharging
a patient immediately restores bed availability across all terminals.

4.3.5 Nursing Vitals & Pre-Consultation Triage Module:
Operating as the clinical bridge between registration and consultation, this module allows nursing officers to:
- Review outpatient queues awaiting pre-consultation vitals triage.
- Record physiological parameters: systolic and diastolic blood pressure, SpO2, pulse rate, blood glucose, and temperature.
- Highlight out-of-range physiological values with visual warning banners.
- Finalize assessments to advance patients into the assigned physician's consultation queue.

4.3.6 Doctor Outpatient Consultation & Write Rx Module:
The physician consultation console enables medical practitioners to:
- View real-time patient queues prioritized by arrival time and vital assessment completion status.
- Review pre-consultation vital signs recorded by nurses prior to examining the patient.
- Author structured electronic prescriptions (Write Rx) specifying medication name, dosage form, strength, frequency,
  duration, and clinical notes.
- Access inpatient discharge registers to record post-discharge follow-up care instructions.

4.3.7 Pharmacy Inventory, Stock Approval & Billing Module:
This module manages the pharmaceutical supply chain and dispensing workflows:
- Enables pharmacy staff to submit stock requests that remain pending until approved by an administrator.
- Deducts medication stock atomically upon dispensing, preventing negative inventory balances.
- Generates multi-item pharmacy bills that display all prescribed line items accurately on receipts and invoices.
- Supports both direct point-of-sale payments and Pay-at-Counter routing to the reception desk.

4.3.8 Laboratory Diagnostics & Dynamic Template Module:
This module manages diagnostic laboratory testing with specialized, test-specific templates:
- Automatically loads the appropriate parameter schema based on the ordered test (e.g., CBC, LFT, KFT, Blood Glucose, Lipid Profile).
- Pre-populates physiological reference ranges and highlights abnormal values for clinical review.
- Generates formatted, print-ready diagnostic reports in PDF format.
- Routes laboratory fees through the central counter collection queue when Pay-at-Counter is selected.

4.3.9 Smart Queue Prediction Module:
This module calculates transparent, data-driven wait-time estimates across hospital service queues:
- Doctor Consultation: Calculates wait times at ~15 minutes per waiting patient and flags high load when the queue exceeds 5 patients.
- Nursing Vitals Triage: Estimates wait times at ~6 minutes per patient.
- Pharmacy Dispensing: Projects dispensing times at ~6 minutes per prescription order.
- Laboratory Processing: Calculates turnaround times at ~15 minutes for routine tests and ~30 minutes for comprehensive profiles.

4.3.10 Post-Discharge Follow-Up Care Module:
This module bridges inpatient discharge with continued outpatient care:
- Automatically generates a follow-up record when an inpatient is discharged, defaulting to a 7-day review interval.
- Allows physicians and nurses to document clinical recovery progress notes.
- Enables receptionists to schedule follow-up outpatient visits linked to the original inpatient admission.

4.3.11 Bilingual (Tamil/English) Patient Assistant Module:
This patient-facing module provides an accessible conversational assistant supporting both English and Tamil script:
- Retrieves authenticated appointment dates, queue positions, and doctor specialties.
- Detects emergency keywords (e.g., *chest pain*, *marbhu vali*, *heart attack*, *breathing difficulty*) to immediately
  trigger an emergency triage alert directing the patient to call the 108 Emergency Ambulance service.
- Provides directional navigation guidance across hospital blocks and departments.
- Includes a clear medical disclaimer clarifying that virtual guidance does not replace professional clinical diagnosis.

5.1 ALGORITHMIC FOUNDATIONS AND IMPLEMENTATION METHODOLOGY
----------------------------------------------------------
The implementation of the Niramaya platform is governed by three architectural principles:
1. Transactional Atomicity: All multi-step operations (bed allocation, inventory deduction, payment clearance) are
   wrapped within database transaction blocks (`conn.setAutoCommit(false)` ... `conn.commit()`) with automatic rollback
   on error.
2. Parameterized SQL Execution: Every database query uses prepared statements (`PreparedStatement`) with explicit parameter
   binding, completely eliminating SQL injection vulnerabilities.
3. Separation of Concerns: The backend Java codebase is organized into modular layers: HTTP request routing and JSON
   serialization in `Server.java`, and database access logic in specialized DAO classes (`IpdDAO`, `PharmacyDAO`,
   `LabDAO`, `FollowUpDAO`, `AppointmentDAO`).


5.2 INPATIENT ADMISSION AND CONCURRENCY LOCKING IMPLEMENTATION
--------------------------------------------------------------
The inpatient admission workflow must guarantee that two admissions clerks cannot assign the same bed simultaneously.
This is implemented in [IpdDAO.java](file:///d:/Niramaya_Hospital_Management_System-main/src/main/java/com/hospital/dao/IpdDAO.java)
using pessimistic row-level locking:

```java
// Listing 5.1: Concurrency-Safe Bed Allocation in IpdDAO.java
public static synchronized boolean admitPatient(String patientId, String doctorId, 
                                                String bedId, String notes) {
    String checkLockSql = "SELECT status FROM ipd_beds WHERE bed_id = ? FOR UPDATE";
    String insertAdmitSql = "INSERT INTO ipd_admissions (admission_id, patient_id, doctor_id, "
                          + "bed_id, admission_date, status, admission_notes) "
                          + "VALUES (?, ?, ?, ?, CURRENT_DATE, 'Admitted', ?)";
    String updateBedSql = "UPDATE ipd_beds SET status = 'Occupied' WHERE bed_id = ?";

    Connection conn = null;
    try {
        conn = DBConnection.getConnection();
        conn.setAutoCommit(false); // Begin ACID transaction boundary

        // 1. Acquire pessimistic row-level lock
        try (PreparedStatement checkStmt = conn.prepareStatement(checkLockSql)) {
            checkStmt.setString(1, bedId);
            ResultSet rs = checkStmt.executeQuery();
            if (!rs.next()) {
                conn.rollback();
                return false; // Bed does not exist
            }
            String currentStatus = rs.getString("status");
            if (!"Available".equalsIgnoreCase(currentStatus)) {
                conn.rollback();
                return false; // Reject: Bed is Occupied or under Maintenance
            }
        }

        // 2. Persist admission record
        String admissionId = "ADM-" + UUID.randomUUID().toString().substring(0, 8).toUpperCase();
        try (PreparedStatement admitStmt = conn.prepareStatement(insertAdmitSql)) {
            admitStmt.setString(1, admissionId);
            admitStmt.setString(2, patientId);
            admitStmt.setString(3, doctorId);
            admitStmt.setString(4, bedId);
            admitStmt.setString(5, notes != null ? notes : "Standard Admission");
            admitStmt.executeUpdate();
        }

        // 3. Mark bed as Occupied
        try (PreparedStatement updateStmt = conn.prepareStatement(updateBedSql)) {
            updateStmt.setString(1, bedId);
            updateStmt.executeUpdate();
        }

        conn.commit(); // Commit all changes atomically
        return true;
    } catch (SQLException e) {
        if (conn != null) {
            try { conn.rollback(); } catch (SQLException ex) { ex.printStackTrace(); }
        }
        e.printStackTrace();
        return false;
    } finally {
        if (conn != null) {
            try { conn.setAutoCommit(true); conn.close(); } catch (SQLException e) { e.printStackTrace(); }
        }
    }
}
```

Code Explanation:
1. `conn.setAutoCommit(false)` establishes the transaction boundary.
2. `SELECT status FROM ipd_beds WHERE bed_id = ? FOR UPDATE` places an exclusive row-level lock on the bed record in
   PostgreSQL, forcing concurrent transactions attempting to read or modify that specific bed to wait until this transaction completes.
3. The bed's status is validated: if it is not `'Available'` (e.g., already `'Occupied'` or `'Maintenance'`), the transaction
   is rolled back immediately and returns `false`.
4. If available, the admission record is inserted and the bed's status is updated to `'Occupied'`.
5. `conn.commit()` commits both operations simultaneously. If any error occurs, `conn.rollback()` restores the database
   to its previous state.

5.4 PHARMACY INVENTORY STOCK APPROVAL AND DISPENSING DEDUCTION
--------------------------------------------------------------
The pharmacy inventory architecture enforces a two-tier control workflow: staff submit stock requests, but stock levels
increase only after administrator approval. When medications are dispensed, inventory is deducted atomically:

```java
// Listing 5.3: Atomic Inventory Deduction on Dispense in PharmacyDAO.java
public static synchronized boolean dispensePharmacyOrder(String orderId, String staffId) {
    String queryItemsSql = "SELECT medicine_id, quantity FROM pharmacy_order_items WHERE order_id = ?";
    String checkStockSql = "SELECT stock_quantity FROM pharmacy_inventory WHERE medicine_id = ? FOR UPDATE";
    String deductStockSql = "UPDATE pharmacy_inventory SET stock_quantity = stock_quantity - ? "
                          + "WHERE medicine_id = ?";
    String updateOrderSql = "UPDATE pharmacy_orders SET dispensing_status = 'Dispensed', "
                          + "dispensed_by = ?, dispensed_at = CURRENT_TIMESTAMP WHERE order_id = ?";

    Connection conn = null;
    try {
        conn = DBConnection.getConnection();
        conn.setAutoCommit(false);

        // 1. Fetch line items
        List<Map.Entry<String, Integer>> items = new ArrayList<>();
        try (PreparedStatement pItem = conn.prepareStatement(queryItemsSql)) {
            pItem.setString(1, orderId);
            ResultSet rs = pItem.executeQuery();
            while (rs.next()) {
                items.add(new AbstractMap.SimpleEntry<>(rs.getString("medicine_id"), 
                                                        rs.getInt("quantity")));
            }
        }

        // 2. Validate stock availability and deduct atomically
        for (Map.Entry<String, Integer> item : items) {
            String medId = item.getKey();
            int qtyToDeduct = item.getValue();

            try (PreparedStatement pCheck = conn.prepareStatement(checkStockSql)) {
                pCheck.setString(1, medId);
                ResultSet rsStock = pCheck.executeQuery();
                if (!rsStock.next() || rsStock.getInt("stock_quantity") < qtyToDeduct) {
                    conn.rollback(); // Reject: Insufficient stock
                    return false;
                }
            }

            try (PreparedStatement pDeduct = conn.prepareStatement(deductStockSql)) {
                pDeduct.setInt(1, qtyToDeduct);
                pDeduct.setString(2, medId);
                pDeduct.executeUpdate();
            }
        }

        // 3. Mark order as Dispensed
        try (PreparedStatement pOrder = conn.prepareStatement(updateOrderSql)) {
            pOrder.setString(1, staffId);
            pOrder.setString(2, orderId);
            pOrder.executeUpdate();
        }

        conn.commit();
        return true;
    } catch (SQLException e) {
        if (conn != null) {
            try { conn.rollback(); } catch (SQLException ex) { ex.printStackTrace(); }
        }
        return false;
    } finally {
        if (conn != null) {
            try { conn.setAutoCommit(true); conn.close(); } catch (SQLException e) { e.printStackTrace(); }
        }
    }
}
```

Code Explanation:
1. Queries all line items associated with the order ID.
2. Acquires row locks on each inventory item and verifies that available stock meets or exceeds the required quantity.
3. If any item has insufficient stock, the transaction rolls back immediately, preventing partial dispensing and negative inventory.
4. If stock is sufficient, inventory is deducted and the order is marked `'Dispensed'` within the same atomic transaction.

```javascript
function validateRange(input) {
    const val = parseFloat(input.value);
    const min = parseFloat(input.dataset.min);
    const max = parseFloat(input.dataset.max);
    if (!isNaN(val)) {
        if (val < min || val > max) {
            input.style.borderColor = '#e74c3c';
            input.style.backgroundColor = '#fdebd0';
        } else {
            input.style.borderColor = '#27ae60';
            input.style.backgroundColor = '#eafaf1';
        }
    }
}
```

5.6 SMART QUEUE ESTIMATION ALGORITHM
------------------------------------
The queue prediction engine uses transparent, rule-based formulas to calculate wait-time estimates across hospital services:

```java
// Listing 5.5: Queue Overview Calculation in Server.java
static class QueueOverviewHandler implements HttpHandler {
    @Override
    public void handle(HttpExchange exchange) throws IOException {
        String sqlOpd = "SELECT COUNT(*) FROM appointments WHERE appointment_date = CURRENT_DATE "
                      + "AND status IN ('Scheduled', 'ReadyForConsult')";
        String sqlNurse = "SELECT COUNT(*) FROM appointments WHERE appointment_date = CURRENT_DATE "
                        + "AND status = 'Scheduled'";
        String sqlLab = "SELECT COUNT(*) FROM lab_bookings WHERE booking_date = CURRENT_DATE "
                      + "AND test_status = 'Pending'";
        String sqlPharm = "SELECT COUNT(*) FROM pharmacy_orders WHERE created_at::DATE = CURRENT_DATE "
                        + "AND dispensing_status = 'Pending'";

        try (Connection conn = DBConnection.getConnection()) {
            int opdCount = getCount(conn, sqlOpd);
            int nurseCount = getCount(conn, sqlNurse);
            int labCount = getCount(conn, sqlLab);
            int pharmCount = getCount(conn, sqlPharm);

            // Calibrated service durations (minutes per patient)
            int opdWaitEst = opdCount * 15;
            int nurseWaitEst = nurseCount * 6;
            int labWaitEst = labCount * 15;
            int pharmWaitEst = pharmCount * 6;

            JsonObject res = new JsonObject();
            res.addProperty("opdWaiting", opdCount);
            res.addProperty("opdEstimatedMinutes", opdWaitEst);
            res.addProperty("nurseWaiting", nurseCount);
            res.addProperty("nurseEstimatedMinutes", nurseWaitEst);
            res.addProperty("labWaiting", labCount);
            res.addProperty("labEstimatedMinutes", labWaitEst);
            res.addProperty("pharmacyWaiting", pharmCount);
            res.addProperty("pharmacyEstimatedMinutes", pharmWaitEst);

            sendResponse(exchange, 200, res.toString());
        } catch (SQLException e) {
            sendResponse(exchange, 500, "{\"error\":\"Error calculating queue metrics\"}");
        }
    }
}
```

Code Explanation:
1. Queries active, in-progress queues across outpatient, nursing, laboratory, and pharmacy departments.
2. Applies standard operational service durations (15 min/consultation, 6 min/vitals triage, 15 min/lab test, 6 min/dispense)
   to generate real-time wait-time estimates without fabricating synthetic data.


5.7 BILINGUAL ASSISTANT & EMERGENCY TRIAGE LOGIC
------------------------------------------------
The patient assistant endpoint supports both English and Tamil, featuring keyword-based emergency triage detection:

```java
// Listing 5.6: Bilingual Patient Assistant Handler in Server.java
static class PatientAssistantHandler implements HttpHandler {
    private static final String[] EMERGENCY_KEYWORDS = {
        "chest pain", "heart attack", "unconscious", "cannot breathe", "severe bleeding",
        "stroke", "marbhu vali", "nenju vali", "moochu thinaral", "rathapokku"
    };

    @Override
    public void handle(HttpExchange exchange) throws IOException {
        String body = new String(exchange.getRequestBody().readAllBytes(), StandardCharsets.UTF_8);
        JsonObject json = JsonParser.parseString(body).getAsJsonObject();

        String message = (json.has("message") ? json.get("message") : json.get("query"))
                         .getAsString().toLowerCase().trim();
        String lang = json.has("language") ? json.get("language").getAsString() : "en";
        boolean isTamil = "ta".equalsIgnoreCase(lang);

        // 1. Immediate Emergency Triage Check
        for (String kw : EMERGENCY_KEYWORDS) {
            if (message.contains(kw)) {
                JsonObject alert = new JsonObject();
                alert.addProperty("emergency", true);
                if (isTamil) {
                    alert.addProperty("reply", "அவசர எச்சரிக்கை! உங்களுக்கு உடனடி மருத்துவ உதவி தேவைப்படலாம். "
                                             + "தயவுசெய்து உடனடியாக 108 அவசர ஆம்புலன்ஸ் சேவையை அழைக்கவும்.");
                } else {
                    alert.addProperty("reply", "EMERGENCY ALERT: Your symptoms may indicate a critical medical emergency. "
                                             + "Please call the 108 Emergency Ambulance immediately.");
                }
                alert.addProperty("disclaimer", "Automated Triage. Seek immediate emergency clinical care.");
                sendResponse(exchange, 200, alert.toString());
                return;
            }
        }

        // 2. Authenticated Information Retrieval (Doctor Roster, Queue Status, etc.)
        JsonObject response = processStandardQueries(message, isTamil);
        sendResponse(exchange, 200, response.toString());
    }
}
```

Code Explanation:
1. Scans incoming user messages against pre-defined emergency keywords in both English and Tamil phonetics.
2. If an emergency symptom is detected, the handler bypasses standard response generation and immediately returns an
   emergency alert directing the patient to call the 108 Emergency Ambulance service.
3. Standard informational queries (doctor listings, queue positions, navigation) are processed through database queries
   and returned with localized text and clinical disclaimers.

FRAGMENT 1: Synchronized Database Connection Pool (DBConnection.java)
Demonstrates the thread-safe connection pooling pattern, ensuring reliable database connectivity under concurrent loads.
------------------------------------------------------------------------------------------------------------------------
```java
package com.hospital.dao;

import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.SQLException;
import java.util.ArrayList;
import java.util.List;

public class DBConnection {
    private static final String URL = "jdbc:postgresql://localhost:5432/hospital_db";
    private static final String USER = "postgres";
    private static final String PASS = "password123";
    private static final int POOL_SIZE = 10;
    private static final List<Connection> connectionPool = new ArrayList<>(POOL_SIZE);

    static {
        try {
            Class.forName("org.postgresql.Driver");
            for (int i = 0; i < POOL_SIZE; i++) {
                connectionPool.add(DriverManager.getConnection(URL, USER, PASS));
            }
        } catch (ClassNotFoundException | SQLException e) {
            System.err.println("[FATAL] Database Pool Initialization Failed: " + e.getMessage());
            e.printStackTrace();
        }
    }

    public static synchronized Connection getConnection() throws SQLException {
        for (int i = 0; i < connectionPool.size(); i++) {
            Connection conn = connectionPool.get(i);
            if (conn != null && !conn.isClosed() && conn.isValid(2)) {
                return connectionPool.remove(i);
            }
        }
        // If pool is exhausted, establish a new transient connection
        return DriverManager.getConnection(URL, USER, PASS);
    }

    public static synchronized void releaseConnection(Connection conn) {
        if (conn != null) {
            try {
                if (!conn.isClosed() && connectionPool.size() < POOL_SIZE) {
                    connectionPool.add(conn);
                } else {
                    conn.close();
                }
            } catch (SQLException e) {
                e.printStackTrace();
            }
        }
    }
}
```

Technical Explanation (Fragment 1):
1. Initializes a fixed pool of 10 database connections at class loading time, eliminating the overhead of establishing
   new TCP handshakes for every HTTP request.
2. `getConnection()` iterates through the pool, validating connection liveness (`conn.isValid(2)`) before handing it
   to the calling thread. If the pool is temporarily exhausted, it provisions a transient connection.
3. `releaseConnection()` returns the connection to the pool if space is available or closes it cleanly, preventing
   resource leaks.

FRAGMENT 3: Native Multithreaded HTTP Server Routing & Dispatcher (Server.java)
Demonstrates high-performance REST routing using Java's built-in HttpServer without external servlet containers.
------------------------------------------------------------------------------------------------------------------------
```java
package com.hospital;

import com.sun.net.httpserver.HttpServer;
import com.sun.net.httpserver.HttpHandler;
import com.sun.net.httpserver.HttpExchange;
import java.net.InetSocketAddress;
import java.io.IOException;
import java.io.OutputStream;
import java.nio.charset.StandardCharsets;
import java.util.concurrent.Executors;

public class Server {
    private static final int PORT = 8080;

    public static void main(String[] args) throws IOException {
        HttpServer server = HttpServer.create(new InetSocketAddress(PORT), 0);

        // Core API Context Routing
        server.createContext("/api/auth/login", new AuthHandler());
        server.createContext("/api/ipd/beds", new IpdBedsHandler());
        server.createContext("/api/ipd/admit", new IpdAdmitHandler());
        server.createContext("/api/ipd/discharge", new IpdDischargeHandler());
        server.createContext("/api/queue/overview", new QueueOverviewHandler());
        server.createContext("/api/assistant/chat", new PatientAssistantHandler());

        // Configure dynamic thread pool for concurrent request handling
        server.setExecutor(Executors.newFixedThreadPool(20));
        server.start();
        System.out.println("[SERVER] Niramaya HTTP Engine listening on port " + PORT);
    }

    public static void sendResponse(HttpExchange exchange, int statusCode, String responseText) 
            throws IOException {
        byte[] bytes = responseText.getBytes(StandardCharsets.UTF_8);
        exchange.getResponseHeaders().set("Content-Type", "application/json; charset=UTF-8");
        exchange.getResponseHeaders().set("Access-Control-Allow-Origin", "*");
        exchange.sendResponseHeaders(statusCode, bytes.length);
        try (OutputStream os = exchange.getResponseBody()) {
            os.write(bytes);
        }
    }
}
```
